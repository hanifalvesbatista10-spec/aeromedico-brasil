# Frete automático (Melhor Envio) — plano de implementação

> **Para quem executa:** use `superpowers:executing-plans` (ou `subagent-driven-development`). Os passos usam caixas `- [ ]`.

**Objetivo:** o cliente informa o CEP no carrinho, vê as opções de entrega com preço e prazo calculados pelo Melhor Envio a partir do peso e das medidas dos produtos, escolhe uma e vê o total com frete.

**Arquitetura:** uma interface `ShippingProvider` (trocável) com a implementação do Melhor Envio. Peso e medidas vêm do banco (nunca do navegador): a Server Action recalcula o carrinho, monta os itens e consulta a API com o token guardado só no servidor (variável de ambiente, sem `NEXT_PUBLIC`). **Sem token configurado não há cotação inventada**: a loja continua combinando o frete pelo WhatsApp. O pacote é enviado como lista de produtos (cada um com suas medidas e quantidade); o Melhor Envio faz a composição dos volumes.

**Tech Stack:** Next.js 16, TypeScript, Zod, `fetch` nativo, Vitest + Testing Library. **Sem dependência nova. Sem migration.**

**Spec:** `docs/superpowers/specs/2026-10-17-loja-mentoria-area-cliente-design.md` (frete pela Melhor Envio a partir de peso e tamanho; total com frete; sem token, não inventar tabela: "tabela de reserva" fica como decisão do cliente, ver Restrições). Planos anteriores: `2026-10-20-carrinho.md`, `2026-10-20-cupom.md`.

**Contrato da API (conferido em docs.melhorenvio.com.br, "Cálculo de fretes por produtos"):** `POST https://melhorenvio.com.br/api/v2/me/shipment/calculate` (sandbox: `https://sandbox.melhorenvio.com.br/...`); cabeçalhos `Accept: application/json`, `Content-Type: application/json`, `Authorization: Bearer <token>` e **`User-Agent` obrigatório** (nome da aplicação + e-mail técnico); corpo `{ from: { postal_code }, to: { postal_code }, products: [{ id, width, height, length, weight, insurance_value, quantity }], options: { receipt: false, own_hand: false } }` com dimensões em **cm**, peso em **kg**, `insurance_value` em reais (2 casas) **por unidade** (a API multiplica pela quantidade); resposta: lista de `{ id, name, price, custom_price, discount, currency, delivery_time, delivery_range, custom_delivery_time, company: { id, name }, error? }` — usar `custom_price` e `custom_delivery_time` quando existirem; falha de validação volta HTTP 422 com `message`/`errors`.

## Restrições globais

- Segredos só em variáveis de ambiente do servidor: `MELHOR_ENVIO_TOKEN`, `MELHOR_ENVIO_ENV` (`production` ou `sandbox`; ausente = `sandbox`), `STORE_ORIGIN_CEP`, `MELHOR_ENVIO_CONTACT_EMAIL`. Nunca ler/imprimir valores; citar só os nomes. `.env.example` ganha os nomes, sem valores.
- Nunca confiar em peso, medida ou preço enviados pelo navegador: tudo vem do banco.
- Sem dado inventado: sem configuração completa, a ação responde "não configurado" e a tela mantém "frete combinado no WhatsApp". Nenhuma tabela de frete com valores inventados.
- Valores em centavos; `formatBRL` na tela.
- Erros esperados voltam como valor `{ ok, ... }`; a mensagem do fornecedor externo nunca vai para o cliente.
- Interface em pt-BR; textos novos marcados **[copy]** passam pelo `copy-editor-ptbr`.
- Trabalhar na `main`; commits locais; **sem push** sem aprovação.

## Foco de revisão

1. CEP digitado de qualquer jeito ("01018-020", " 01018020 ", "0101", letras): normalizado ou recusado com mensagem, sem chamar a API. (Tasks 1 e 3)
2. API do Melhor Envio fora do ar, lenta (timeout), 401/403, 422 ou resposta fora do formato: o carrinho continua funcionando e o cliente recebe uma mensagem clara, sem texto do fornecedor. (Tasks 2 e 3)
3. Serviços que voltam com `error` ou sem preço (ex.: serviço que não atende o CEP): ignorados, sem derrubar as demais opções. (Task 2)
4. Carrinho mudou depois da cotação: o frete antigo não vale mais e não entra no total. (Task 5)
5. Produto sem peso/medida útil ou item indisponível no carrinho: só os itens válidos entram na cotação; carrinho sem item válido não consulta a API. (Tasks 1 e 3)

**Files:**

- Produces:
  ```ts
  export interface MelhorEnvioConfig {
    token: string; environment: "sandbox" | "production";

  export function getShippingProvider(): ShippingProvider | null    // lê process.env
  ```
  Regras: URL `{base}/api/v2/me/shipment/calculate`; método `POST`; cabeçalhos `Accept`, `Content-Type`, `Authorization: Bearer <token>`, `User-Agent: "Aeromedico Brasil (<contactEmail>)"`; corpo `from.postal_code` e `to.postal_code` com 8 dígitos; cada produto `{ id, width, height, length, weight: gramas/1000, insurance_value: centavos/100, quantity }`; `options: { receipt: false, own_hand: false }`; **sem** `services`. Resposta: ignora elementos com `error`, sem preço ou preço inválido/negativo; preço = `custom_price ?? price` (número ou texto com ponto decimal) → centavos arredondados; prazo = `custom_delivery_time ?? delivery_time` (inteiro ≥ 0, senão `null`); `company` = `company.name` (senão `""`); ordena do mais barato ao mais caro (empate: menor prazo). Provedor: `fetch` com `signal: AbortSignal.timeout(8000)`; HTTP 422 → `{ ok:false, reason:"invalid-cep" }`; 401/403, 5xx, timeout, rede ou corpo que não é lista → `{ ok:false, reason:"unavailable" }` (e `console.error` sem token); lista vazia ou sem opção válida → `{ ok:false, reason:"unavailable" }`. Config: exige `MELHOR_ENVIO_TOKEN` não vazio, `STORE_ORIGIN_CEP` que normaliza, `MELHOR_ENVIO_CONTACT_EMAIL` com `@`; `MELHOR_ENVIO_ENV === "production"` → produção, qualquer outro valor/ausente → sandbox; faltando algo → `null`.
